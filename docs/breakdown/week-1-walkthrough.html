Week 1 — The Walking Skeleton

The complete agent, built from four layers. By the end of this page you'll understand exactly how a stateless text model becomes an agent that calls tools — every layer, with the real code, the same way it was taught line by line.

§ What an "AI harness" actually is

An LLM by itself is stateless text-in, text-out. You give it words, it gives you words back. It can't remember, can't act, can't use a tool. A harness is the runtime that wraps the model and turns it into an agent. Claude Code is a harness. Cursor's agent mode is a harness. ankus is a harness you build yourself so every piece is legible.

The minimum a harness must do is three things, and Week 1 builds all three:

  • Hold the conversation — track messages as they accumulate (Layer 1).
  • Offer tools — let the model request actions, and run them (Layer 2).
  • Talk to a model — translate to whatever LLM you plug in (Layer 3).
  • Loop — tie it together: ask, run tools, ask again, until done (Layer 4).

§ The mental model — the harness is a loop

Strip away everything and an agent is this. Read it once; the whole week is just the four layers that make these lines possible:

# the whole agent, in spirit
messages = [system_prompt]
while True:
    response = provider.complete(messages, tools)   # ask the model
    messages.append(response)
    if not response.wants_tools:                     # it just talked → done
        return response.text
    for call in response.tool_calls:                 # it ordered tools → run them
        result = registry.execute(call)
        messages.append(result)                      # feed the outcome back, loop again

The layers stack bottom-up — each depends only on the one below it:

1 · Messages — the shared vocabulary

Two different LLM APIs (Anthropic and Ollama) describe the same conversation with different JSON shapes. If the loop spoke one API's shape, swapping models would mean rewriting the loop. So ankus invents its own neutral shape that everything inside speaks; the providers translate at the edges.

Analogy — a conversation is a list of turns

Talking to an agent is like any chat: turn 1 you speak, turn 2 the model "goes to check something," turn 3 the tool answers, turn 4 the model replies. This file defines what one turn looks like in Python. That's all it is.

Three kinds of thing flow through a conversation, so there are three classes:

Python aside — @dataclass

@dataclass auto-writes the boilerplate constructor for a data-holding class. You just declare the fields (id: str) and Python writes __init__ for you. The : str is a type hint — documentation, not enforced at runtime.

ToolCall — "the model wants to run a tool"

core/messages.py
@dataclass
class ToolCall:
    id: str          # a label, e.g. "c1" — the order-ticket number
    name: str        # which tool, e.g. "get_current_time"
    arguments: dict  # what to pass it, e.g. {"timezone": "Asia/Tokyo"}

The single most important idea in the whole project lives here: the model can never run anything. It only produces text. When it "wants" a tool, all it can do is emit a request — a ToolCall. The harness decides whether and how to actually run it.

Analogy — ordering at a restaurant

You (the model) can't walk into the kitchen and cook. You hand the waiter (the harness) a written order. The ToolCall is that order ticket. The id exists because you might order three dishes at once — the ticket number matches each returned plate to its order.

ToolResult — "here's what the tool produced"

core/messages.py
@dataclass
class ToolResult:
    tool_call_id: str   # "c1" — matches the ToolCall's id
    name: str
    content: str        # "2026-07-14 21:04:50 JST" — the actual answer
    is_error: bool = False

The plate coming back from the kitchen. tool_call_id carries the same ticket number so everyone knows which order it answers.

Why is_error matters

If the kitchen is out of an ingredient, the waiter comes back and says "sorry, here's why" instead of throwing the plate on the floor (crashing). is_error=True lets the model see the failure and adapt. This is why an agent doesn't crash when a tool fails — the failure is just another message. Remember this; it comes up in every layer.

Message — "one turn in the conversation"

core/messages.py
@dataclass
class Message:
    role: Role                        # WHO: "system" | "user" | "assistant" | "tool"
    text: str = ""                    # WHAT they said (plain words)
    tool_calls: list[ToolCall] = ...  # only the assistant fills this (its orders)
    tool_call_id: str | None = None   # only "tool" turns
    name: str | None = None
    is_error: bool = False

The role says who is speaking: system (the standing instructions), user (the human), assistant (the AI), tool (a result coming back). A complete conversation is just a Python list of these — that list is the agent's entire memory:

messages = [
    Message(role="system",    text="You are a concise assistant."),
    Message(role="user",      text="What time is it in Tokyo?"),
    Message(role="assistant", tool_calls=[ToolCall(id="c1", name="get_current_time",
                                                   arguments={"timezone": "Asia/Tokyo"})]),
    Message(role="tool",      text="2026-07-14 21:04:50 JST", tool_call_id="c1"),
    Message(role="assistant", text="It's 9:04 PM in Tokyo."),
]
The empty-text tool call

Notice the third message: text is empty, tool_calls is filled. That's the model placing an order, not talking to the human. An assistant turn can talk, act, or both — which is why Message has both a text field and a tool_calls field. The one question the loop ever asks is: "are there any tool_calls?" — that's the property wants_tools, the hinge of the entire agent.

2 · Tools — what the model can actually DO

A model alone only produces text. Tools are how it touches the world. Layer 2 answers the question Layer 1 left open: when the model places an order like ToolCall(name="get_current_time"), who cooks it, and how does the model know what's on the menu?

A tool is a thing with 4 parts

tools/base.py
class Tool(ABC):
    name: str          # how the model refers to it
    description: str    # the model READS this to decide WHEN to use it
    input_schema: dict  # JSON Schema — tells the model what arguments are valid
    def run(self, arguments: dict) -> str: ...  # the actual work
Analogy — a dish on a menu

name = the dish's name · description = the menu blurb (so you know when to order it) · input_schema = the customization options · run() = the kitchen that cooks it. Every tool in ankus has exactly these four parts. ABC ("Abstract Base Class") makes Tool a fill-in-the-blank template you can't create directly — a safety net guaranteeing every real tool has all four parts.

The description is prompt engineering, not a comment

The model literally reads description to decide whether a tool fits the task. A vague description = a confused model. It's the most important string you write for a tool.

The @tool decorator — write a function, get a tool

tools/builtin/clock.py
@tool()
def get_current_time(timezone: str = "UTC") -> str:
    """Return the current date and time in the given IANA timezone."""
    ...

That one @tool() line reads the function's signature and builds all four parts automatically:

get_current_time.name          # "get_current_time"   (the function name)
get_current_time.description   # the docstring
get_current_time.input_schema  # {"type": "object",
                              #  "properties": {"timezone": {"type": "string"}}}
                              # no "required": timezone has a default → optional
The rule

A parameter without a default becomes required; with a default it's optional. The Python type hint (str) maps to the JSON type ("string"). You write a normal function; you get a model-callable tool.

The registry — the switchboard

At heart the registry is one dictionary: name → Tool. It does two jobs.

tools/registry.py
def schemas(self):            # JOB 1: hand the model the MENU
    return [{"name": t.name, "description": t.description,
             "input_schema": t.input_schema} for t in self._tools.values()]

def execute(self, call):      # JOB 2: run an order — and NEVER crash
    tool = self._tools.get(call.name)
    if tool is None:                             # model hallucinated a tool name
        return ToolResult(..., content="Unknown tool...", is_error=True)
    try:
        content = tool.run(call.arguments)       # success
        return tool.to_result(call.id, content)
    except Exception as exc:                     # tool threw (e.g. bad timezone)
        return tool.to_result(call.id, f"{exc}", is_error=True)
The most important property in Layer 2 — execute NEVER raises

If a tool crashes, that would crash the whole agent — one bad call throws away the entire conversation. Instead, execute catches any failure and turns it into an error ToolResult. The failure becomes just another message the model sees and can recover from. In an agent, errors are not exceptions to crash on — they are observations to feed back.

3 · Providers — the translator / firewall

Inside ankus everything speaks the neutral Message language. But the actual LLM doesn't — Claude wants one JSON shape, Ollama wants another. A Provider is the translator that sits at the border. It does exactly one job:

providers/base.py
class Provider(ABC):
    @abstractmethod
    def complete(self, messages: list[Message], tools: list[dict]) -> Message: ...
    # neutral conversation + neutral menu  →  call the backend  →  one neutral reply

Read the signature as a sentence: take the whole conversation and the tool menu, call the model, return one assistant Message. Neutral in, neutral out. The agent loop never imports anthropic, never talks HTTP — it only ever calls provider.complete(...).

The same neutral tool-result becomes two completely different native shapes — and the loop above never sees either one:

# SAME neutral input:
Message(role="tool", text="2:30 PM", tool_call_id="c1", name="get_current_time")

# OllamaProvider turns it into:            AnthropicProvider turns it into:
{"role": "tool",                        {"role": "user", "content": [
 "content": "2:30 PM",                     {"type": "tool_result",
 "tool_name": "get_current_time"}           "tool_use_id": "c1",
                                            "content": "2:30 PM"}]}
# (matched by ORDER)                       (matched by ID, folded into a user turn)
Why the neutral format exists — the whole architecture in one idea

The neutral Message is a firewall. Provider differences are quarantined inside each provider's translate helpers. Everything above — the loop, tools, permissions, hooks — lives in a world with one message format. To add a new backend (OpenAI, a local Llama), you write one file and change nothing else. That's what "provider-agnostic" means in code, not slides. (This is the classic Adapter pattern.)

4 · The Loop — tying it together

Now the loop reads almost trivially, because Layers 1–3 did all the hard work. The whole agent is ~7 real lines:

core/agent.py
def run(self, user_message):
    self.messages.append(Message.user(user_message))         # record the human turn

    for _ in range(self.max_steps):                          # safety rail vs infinite loops
        response = self.provider.complete(self.messages, self.registry.schemas())  # ① ask
        self.messages.append(response)                       # ② remember

        if not response.wants_tools:                         # ③ done?
            return response.text                             #    no tools → final answer

        for call in response.tool_calls:                     # ④ run each tool, feed back
            result = self.registry.execute(call)
            self.messages.append(Message.from_tool_result(result))

Four beats: ① ask (Layer 3 hides all translation) · ② remember · ③ the wants_tools hinge (return, or continue) · ④ run tools (Layer 2, never crashes) and append results (Layer 1). Then loop — and now the model can see the tool results in self.messages.

Why the loop is so short

Complexity was pushed down into well-named, single-purpose modules, so the thing on top reads like plain English. The loop is the conductor; the layers are the orchestra. Permissions and hooks (Week 3) slot into the two marked points — before execute, and around each step — without changing this shape. max_steps caps a runaway agent that never stops calling tools.

▶ One request, traced

Now watch all four layers move together. You run agent.run("What is the current time in Tokyo?"). The memory list grows from 1 message to 5:

system
"You are a concise assistant…" — seeded when the Agent was built (1 msg)
user
"What is the current time in Tokyo?" — added by run() (2 msgs). Enter the loop.
assistant
① Provider translates the 2 messages + menu → native → calls Qwen → back to neutral. Model returns: get_current_time({timezone:"Asia/Tokyo"}). ③ wants_tools? YES → don't return (3 msgs)
tool
④ registry.execute runs clock.py → "2026-07-14 21:04:50 JST", appended. Loop back to ① (4 msgs)
assistant
① Ask AGAIN — now the model sees the tool result → writes "It's 9:04 PM in Tokyo." with no tool call. ③ wants_tools? NO → return ✅ (5 msgs)
Proven live on Qwen 2.5 7B (your RTX 2060)

A local 7-billion-parameter model, given only the tool schema (not even told about the tool in the system prompt), decided on its own to call get_current_time, picked the correct IANA timezone Asia/Tokyo, read the result, and answered. The same agent code runs on Claude by swapping one line — the provider object.

This is what makes it an agent, not a Q&A box

The model "thought" across two turns: turn 1 = "I need data, fetch it"; turn 2 = "now I have it, here's the answer." The loop stitched them together by feeding the tool result back. That feedback — append the result, ask again — is the agent.

✦ The big ideas of Week 1

  • A conversation is a growing list[Message] — the agent's only memory. Everything reads it or appends to it.
  • The model can only request tools (a ToolCall), never run them. That separation is what makes permissions possible later.
  • Errors are observations, not crashes — execute turns every failure into a result the model can adapt to.
  • The neutral format is a firewall — provider quirks are quarantined in adapters, so the model backend is swappable in one line.
  • Push complexity down — the loop stays ~15 lines because every hard thing lives in a well-named module beneath it.
